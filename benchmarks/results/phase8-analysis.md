# Phase 8: website-analysis query latency and plans

Measured on 2026-11-08 (UTC) with `benchmarks/analysis.py` and `benchmarks/analysis_index_ab.py`;
method in [`../README.md`](../README.md). These numbers describe this development machine and this
synthetic dataset only. They are not a capacity claim for any other setup, and they vary between
runs (see the two A/B baselines below).

## Environment

- AMD Ryzen 7 5800U laptop (8 cores, 16 threads), Windows 10 Home 10.0.19045; the WSL 2 VM sees
  16 CPUs and 7 GB of memory.
- Python 3.13.7 (`backend/.venv`). PostgreSQL 18.6 in Docker inside WSL 2 (Ubuntu 24.04), reached
  through WSL's localhost forwarding; default PostgreSQL settings of the development container.
- Dataset (seed 11, generated by the script): one job of 1,000 pages and one of 10,000 pages, each
  page with 50 distinct links (80% to pages, 8% to non-page URLs, 7% to URLs never admitted, 5%
  external). Non-page URLs: 404s for 5% of the pages, redirects for 2%, 503s, read timeouts and
  robots.txt refusals for 1% each. Rows: 1,100 crawl URLs and 50,000 links; 11,000 crawl URLs and
  500,000 links. `VACUUM (ANALYZE)` after loading.
- Each case ran 20 times in a row on one database session, as the API calls it (one read-only
  REPEATABLE READ transaction per call). Times are wall times of the service call, in ms.

## What changed, and why

The first measurement (the Phase 8 code before any optimization; raw output
[`phase8-analysis-baseline.json`](phase8-analysis-baseline.json), plans
[`phase8-analysis-baseline-plans.txt`](phase8-analysis-baseline-plans.txt)) found:

1. **Generic plans.** The links listing took 66 to 71 ms for its first five calls on a connection
   and 213 to 258 ms after that (1,000 pages); 247 to 282 ms, then 2,102 to 2,306 ms (10,000
   pages). asyncpg prepares each statement once per connection, and after five executions
   PostgreSQL switched to a generic plan, which cannot drop the optional filters
   (`CAST(:x AS ...) IS NULL OR ...`). Fix: every analysis transaction sets
   `plan_cache_mode = force_custom_plan`.
2. **The links listing classified every link of the job** to return one page of 50. Fix: without a
   filter on the class (or on `verified` or `redirected`), the page is cut first; only its links
   are classified.
3. **Broken links classified every link.** Fix: only links whose target's redirect chain ends in a
   404 or 410 can be broken; those are looked up by target and classified as all others.
4. **The link graph counted degrees for every node** before cutting the node list. Fix: degrees are
   counted for the returned nodes only, and edges are read through the returned pages.
5. **Indexes** (migration 0005, after the A/B below): `pages (job_id, normalized_url)` replaces
   `pages (job_id)`; `page_links (job_id, target_normalized_url)` gains `INCLUDE (is_internal)`.

The final run below is of the final code, which also has the fixes of the independent review
(redirect chains followed for at most 20 redirects, the 1xx status bucket, the link filters).

| links: one source page | 9.8 (9.4-10.9) | 6.8 (6.7-7.6) | 34.3 (33.5-40.1) | 8.6 (8.4-9.6) |

| statistics | 82.3 (80.2-89.7) | 76.6 (73.9-95.1) | 1,178.0 (1,102.8-1,303.1) | 592.7 (577.7-627.4) |

At 1,000 pages (the default page budget, `SITESCOPE_CRAWL_MAX_PAGES_LIMIT`), every case answers in
under 90 ms at the median except the link graph at its maximum limits (2,000 nodes and 10,000
edges: 148 ms). The graph at 1,000 pages did not improve (83 ms before, 88 ms after): counting
degrees per returned node costs about what counting them for all nodes did at that size.

What still grows with the job: a links listing filtered on the class (or on `verified` or
`redirected`) classifies every link of the job, the statistics count and classify all of them,
and the broken links follow the redirect chains of every crawl URL (but classify only the links
of targets that ended in 404 or 410). These are linear in the size of the job: 0.2 to 0.6 s at
500,000 links. A job much larger than that would reach `SITESCOPE_ANALYSIS_TIMEOUT_SECONDS`
(10 s) and get `503 analysis_timeout`; precomputed summaries would be the next step (not built).

## The indexes: A/B

`benchmarks/analysis_index_ab.py` builds revision 0004 (before migration 0005), loads the
10,000-page job once, and measures every case (10 calls, p50 in ms) with the indexes of 0004,
with candidate A, with candidate B instead, and with the indexes of 0004 again. The query code is
the final one. Raw output: [`phase8-index-ab.json`](phase8-index-ab.json).

| Case | 0004 | A: `pages (job_id, normalized_url)` | B: `INCLUDE (is_internal)` | 0004 again |
|---|---|---|---|---|
| links: first 50 | 101.9 | **7.2** | 110.9 | 117.8 |
| links: 50 after a deep cursor | 59.2 | **7.3** | 65.4 | 68.6 |
| link graph: 500 nodes, 2,000 edges | 318.0 | 310.7 | **131.9** | 295.6 |
| link graph: 2,000 nodes, 10,000 edges | 449.6 | 429.8 | **238.6** | 415.7 |
| statistics | 1,078.6 | 1,088.3 | **573.5** | 1,065.9 |
| pages: first 50 | 17.1 | 13.8 | 14.8 | 14.1 |
| pages: 50 after a deep cursor | 11.6 | 10.8 | 10.8 | 10.8 |
| links: one source page | 7.8 | 7.2 | 7.4 | 9.4 |
| links: class `broken`, first 50 | 287.9 | 280.7 | 273.3 | 271.0 |
| broken links: first 50 | 169.5 | 173.6 | 161.8 | 159.7 |

The last five cases do not use the candidate indexes differently; their variation between the
four variants (up to 3.3 ms on the listings under 20 ms, up to 9% on the others) is the noise of
this machine, as the two runs of 0004 show.

- **A** lets PostgreSQL read a job's pages in URL order and stop after one page of links, instead
  of joining and sorting all 500,000. It replaces `ix_pages_job_id` (its first column serves every
  query of that index), so the number of indexes is unchanged.
- **B** makes counting and grouping a job's internal links an index-only scan once the visibility
  map is set (here by `VACUUM`; in normal operation by autovacuum). Before that, the scan visits
  the heap as it did without the included column; nothing gets slower. It replaces the index of
  the same key.

## Query plans

[`phase8-analysis-plans.txt`](phase8-analysis-plans.txt) holds `EXPLAIN (ANALYZE, BUFFERS)` of
every analysis statement on both datasets (custom plans, final code and indexes). At 10,000 pages:

- **links: first 50**: an index scan of `ix_pages_job_id_normalized_url`, a nested loop into each
  page's links (`pk_page_links`), an incremental sort, and a limit after 51 rows; the
  classification then runs for those rows only.
- **broken links**: the redirect chains of all 11,000 crawl URLs (11,200 chain rows, about 6 ms),
  then the links of the 500 targets that answered 404 (20,079 links), looked up through
  `ix_page_links_job_id_target`, and classified.
- **statistics: link totals and most linked**: index-only scans of `ix_page_links_job_id_target`
  (`Heap Fetches: 0` after `VACUUM`).

EXPLAIN ANALYZE adds timing overhead, so its times are higher than the service's.
